Product Overview

An AI front desk that books real appointments — by voice or by typing.

ADAR means Agentic orchestration, live Data, reliable Access, and domain Reasoning. A caller can ask naturally for availability, book a time, reschedule, or cancel — the assistant checks real slots, holds one, and confirms the details back before anything is locked in.

Agentic

ADK Orchestration

One JSON file, one compiler, one scheduling agent.

A two-pass compiler reads agents_config.scheduling.json, builds the tool-bearing agent first, then wires the orchestrator to it — no routing logic hand-written in Python. The orchestrator's own instruction text is the router: send everything to scheduling_agent.

find_practice

Common question: "This is Riverside Family Medicine, right?"

How it works: resolves the caller's practice from name and context, so a multi-practice deployment routes to the right calendar.

check_availability

Common question: "What times does Dr. Patel have Tuesday afternoon?"

How it works: queries live Firestore slots for that provider and appointment type, returning each one with a raw timestamp bracketed alongside the readable time.

hold_slot / confirm_booking

Common request: "Book me for 2:30."

How it works: holds the slot inside a Firestore transaction, confirms name, phone, and email back, then locks it in — two callers can never win the same slot.

reschedule / cancel / lookup

Common request: "Actually move that to Friday." · "Cancel my 3 o'clock."

How it works: re-resolves the existing booking first, then applies the same transactional safety before changing it.

Booking Safety

LLM judgment for the conversation. Database transactions for the booking.

The model decides what the caller wants and carries the booking state — which practice, which provider, which slot — across the conversation. But the actual write that locks a slot is a Firestore transaction, so a race between two callers resolves safely instead of double-booking.

Hold requestedCaller picks a bracketed slot_start_iso value.
Transaction opensFirestore checks the slot is still free.
Details confirmedName, phone, and email read back to the caller.
Commit or rejectA losing caller is told the slot is gone — never silently overwritten.
Confirmation emailSent only after the transaction commits, never before.
